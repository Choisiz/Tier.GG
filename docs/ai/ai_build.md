## 6. 설계와 달랐던 점과 사용자 결정

> Build 때 테스트를 코드에 맞추지 않고 설계 값 단언 3개를 `todo`로 남겨 보고했다. 2026-11-02 사용자가 아래처럼 정해, todo를 정식 테스트로 바꾸고 `feedback_design.md`를 고쳤다.

### 6-1. 세나 판 0~15분 딜 등급 (설계 9장 계산 방식)

- 원인: 설계 9장은 딜 비중을 **정수 %로 반올림한 뒤**(15.25 → 15, 12.54 → 13) 기대 비중과 비교했다. 5-2 규칙("3%p 이상 낮으면 못함")을 반올림 전 값에 적용하면 0~15분은 −2.75%p라 C다.
- 영향: 딜 D(15점) → C(22.5점), 교전 총점 17.5 → 25. 판정(부족)은 같다. 다만 딜이 C가 되어 "부족한 점"에서 빠지고, 말할 순서가 `딜 → 시야`에서 `시야 → 이득 여부`로 바뀐다.
- **결정: 반올림 전 값으로 판정 유지.** 설계 9장을 엔진 결과(딜 C 22.5, 교전 총점 25, 부족한 점 시야 → 이득 여부)로 고쳤다. 2단계 LLM 문장에서 비중을 정수로 쓰면 "−3%p인데 보통"처럼 보일 수 있으니 facts의 소수 값(`diff0: -2.75`)을 쓰게 한다.

### 6-2. 결정적 장면 고르는 순서 (2-1 문장 vs 9장 예시)

- 2-1 문장 그대로("후보 전체를 격차 변화 큰 순, 같으면 킬 많은 순")면 세나 판 3번째가 **18.4분 싸움(킬 5, 격차 −2,331)**이 되어 9장의 22.2분 싸움(킬 8, −465)과 다르다.
- 9장의 이유 열(격차 1위 · 격차 2위 · 킬 수 1위)에 맞춰 **① 격차 3,000 이상 후보를 격차 순 → ② 남은 자리는 킬 5개 이상만 충족한 후보를 킬 수 순**으로 구현했다. **결정: 지금 구현 유지.** 설계 2-1 문구를 이 규칙으로 고쳤다.

### 6-3. 검산 스크립트의 영혼 용 판정 버그 → 경계값 영향

- 설계 5-3은 영혼 용을 "팀의 4번째 용, 그 처치 직후 `DRAGON_SOUL_GIVEN` 이벤트"로 적었다. 실제 16.21 판에서는 **두 번째 용 직후 `teamId: 0`인 `DRAGON_SOUL_GIVEN`**(영혼 속성 공개, 예: `name: "Hextech"`)이 나온다. 검산 스크립트(`analyze.py`의 `obj_points`)는 "처치 뒤 15초 안 이벤트"로 판정해 **두 번째 용을 영혼 용(50점)으로** 셌다.
- 엔진은 설계의 뜻대로 "그 팀의 4번째(장로 제외) 용"으로 센다. 세나 판 값(5:105 등)은 두 방식이 같다.
- 실제 200판 중 185판에서 두 방식이 달랐다. 스크립트로 정한 경계값은 이 버그의 영향을 받았다:

| 경계 (20/40/60/80% 지점) | 설계 (스크립트 방식) | 4번째 용 방식으로 다시 계산 |
|------|------|------|
| 정글 오브젝트 막타 점수 (5-3) | 10 / 32 / 72 / 122 | 10 / 22 / 42 / 82 |
| 교전 이득 여부 우리 팀 몫 % (5-4) | 22 / 42 / 64 / 81 | 24 / 40 / 64 / 78 |

- **결정: 재계산 값 적용.** `rules.ts` 정글 오브젝트 `[82, 42, 22, 10]`, 교전 이득 `[78, 64, 40, 24]`. 설계 5-3·5-4 경계와 12장에 "검산 스크립트 영혼 용 판정 오류 수정, 재계산"을 기록했다. 세나 판 등급 변화 없음. 같은 판 마스터 이(정글) 52점은 C → B.

### 6-4. 말할 순서 기준 (참고, 9장 고침)

- 9장은 "딜(60 중 45점 손실)"처럼 **만점 대비 손실**로 말했고, 승인된 B-1은 "반영 비율 × (등급 점수 − 50%)"(평균 대비)다. 엔진은 B-1을 따르고, 같으면 반영 비율 큰 순으로 정했다. 9장 문구도 B-1 기준으로 고쳤다.

### 6-5. 중후반 파밍 분모 (참고)

- 6-1 경계를 만든 `macro.py`는 "15분 이후 분"을 프레임 개수(`last − 15`)로 셌는데, 마지막 프레임은 정각이 아니라 게임 끝 시각이라 실제보다 길다(200판 중앙값 1.04배, 최대 1.15배). 엔진은 실제 경과 시간으로 나눈다(설계 문구 그대로). 그래서 같은 판이면 엔진 값이 스크립트보다 약 4% 높게 나온다. 경계 재보정 때 함께 맞추면 된다.

## 10. 남은 문제 (1단계)

1. 두 번째 판 `KR_8408851980` fixture는 timeline에 스냅샷·킬·와드 이벤트가 없어 불변 조건(10명 오류 없음·총점 범위·비율 합)만 확인된다. 실제 값 검증은 세나 판 10명으로 보강했다. 손검산할 판을 2~4개 더 넣으려면 Riot 원본이 필요하다(K-1).
2. 교전 이득 여부의 "이긴 팀 평균 73%, 진 팀 평균 29%"(설계 5-4)는 영혼 용 수정 전 값이다. 경계만 재계산했다.
3. 세트(서폿) 덮어쓰기는 보류. 표본이 늘면 다시 판단.
4. 중후반 파밍 경계는 검산 스크립트가 분모를 프레임 개수로 셌던 값이다(6-5, 약 4% 차이). 다음 경계 재보정 때 함께 맞춘다.
5. 총점 경계 70·40은 여전히 초안이다 (설계 11장).
6. (Review 2026-11-02) 딜 구간 평균 등급의 "정확히 중간이면 높은 쪽"(7장 4번)은 Build 해석이다. 같은 판 리 신(정글)은 0~15분 D + 15분~ A → 평균 62.5% → B(좋은 점)가 된다. 사용자 확인이 필요하다(`ai_review.md`).
7. (Review 2026-11-02) 다시하기(조기 항복) 판을 따로 거르지 않는다. 포지션이 있으면 교전·운영 등급이 나온다. 분석 가능한 판 범위(N절 4번)를 정할 때 5단계에서 거른다.
- Review에서 고친 것: `ai_spec.md` B-3 세나 판 재현 행이 사용자 결정 전 값(딜 D, 교전 총점 17.5)으로 남아 있던 것을 결정 뒤 값(딜 C, 25)으로 고쳤다. 코드 변경 없음.

3. **숫자 검사 규칙**: 문장의 숫자는 그 문장 `factIds`의 표기 값과 **값으로** 비교한다(쉼표·소수 표기 차이 무시). 어림은 approx가 있는 fact만: "약/정도 N" = step 반올림 값, "N 넘게/이상/남짓" = 값 > N이고 차이 ≤ step, "N 가까이/미만/이하" = 값 < N이고 차이 ≤ step. 부호(`-`)는 숫자 앞에서만(범위 `15-20`은 부호 아님). 한글 수사 1~10 + 단위(번·명·개·킬·데스·차례·회·판·마리)도 숫자로 보고, "두 번째" 같은 서수는 빼며 "한 번도"는 0으로 본다. 이름 속 숫자("1~3차 포탑", "1대1")는 뺀다. 단위는 Q1에서 검사한다(18장).
