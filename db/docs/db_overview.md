## 1. 한눈에 보기

요약: Riot 게임 원본을 쌓아 두고, 매일 한 번 최근 14일 게임으로 챔피언 통계를 다시 만든다.

```
백엔드 수집기 → 원본 3개 (ranked_players → matches → match_players)
            → [매일 05:00 KST pg_cron] ANALYZE → refresh_window_stats(14)
            → 집계 7개 + champion_tier_view → 백엔드 읽기 API → 프론트
```

| 항목 | 값 |
|------|----|
| DB | Supabase 무료 플랜, PostgreSQL 17.11, 용량 한도 500MB |
| 테이블 | 11개 (원본 3, 집계 7, 운영 1) + 메타 `schema_migrations` |
| 뷰 / 함수 | 뷰 1개, 함수 4개 |
| 원본 | 표본 플레이어 765명 (플래티넘 250, 에메랄드 265, 다이아 250), 게임 3,975개, 참가자 39,750줄 |
| 현재 집계 창 | 2026-10-01 20:00 ~ 2026-10-15 20:00 UTC, **3,789게임** (패치 16.20: 2,640 / 16.19: 1,149) |
| 집계 결과 | 챔피언 × 포지션 606줄 (챔피언 173명), 그중 티어가 나온 줄 187개 (나머지는 50판 미만 "표본 부족") |
| DB 크기 | 90MB (public 테이블 합계 74MB) |
| 마지막 집계 | 2026-10-15 20:00 UTC, 성공, 3.6초 |

## 2. 테이블 구성

요약: 원본은 Riot 값 그대로, 집계는 원본을 센 개수만, 운영은 수집 기록이다. 컬럼은 계약 문서를 본다.

| 묶음 | 테이블 | 역할 | 지금 줄 수 |
|------|--------|------|-----------|
| 원본 | `ranked_players` | 수집 대상 표본 플레이어 1명 = 1줄 | 765 |
| 원본 | `matches` | 게임 1개 (패치, 시작 시각, 처음 찾은 표본) | 3,975 |
| 원본 | `match_players` | 게임 속 플레이어 1명. 게임당 10줄. 챔피언·포지션·승패·밴·스펠·룬·아이템·스킬 순서 | 39,750 |
| 집계 | `stats_window` | 현재 창 1줄 (시작·끝, 게임 수, 집계 시각) | 1 |
| 집계 | `stats_window_patch` | 창 안 패치별 게임 수 | 2 |
| 집계 | `champion` | 챔피언 × 포지션의 pick·win·ban. 티어리스트 | 606 |
| 집계 | `champion_item` | 아이템별 개수 (모든 아이템) | 17,094 |
| 집계 | `champion_rune` | 룬 페이지 조합, 상위 10개 | 3,993 |
| 집계 | `champion_spell` | 소환사 주문 조합, 상위 10개 | 1,555 |
| 집계 | `champion_skill` | 스킬 앞 11레벨 순서, 상위 10개 | 3,349 |
| 운영 | `collection_logs` | 수집 실행 1회 = 1줄 (`running` / `done` / `key_expired` / `failed`) | 10 |

- 컬럼, 타입, PK·FK, CHECK: [`db_contract.md`](../../docs/contracts/db_contract.md) 2~4장, [`db_contract.dbml`](../../docs/contracts/db_contract.dbml)
- 백엔드 저장 규칙 (5분 미만 제외, 한 게임 = 한 트랜잭션 등): 계약 7장
- 원본과 집계는 FK로 잇지 않는다. 집계 함수가 원본을 읽어 집계를 통째로 다시 만든다.
- 이름·이미지는 저장하지 않는다. ID는 모두 Data Dragon 값이다.

## 3. 데이터 흐름과 일정

요약: 백엔드가 원본을 넣고, DB 예약 작업이 매일 집계한다. 오래된 원본 삭제는 사람이 직접 한다.

| 단계 | 누가 | 언제 | 하는 일 |
|------|------|------|---------|
| 수집 | 백엔드 (`npm run collect -- run …`) | 사용자가 직접 실행 (개발 키 24시간) | 최근 14일 솔로랭크 게임만 받아 `matches` 1줄 + `match_players` 10줄을 한 트랜잭션으로 저장 |
| 집계 | pg_cron 작업 `tiergg_daily_refresh` | **매일 05:00 KST (20:00 UTC)** | `SET statement_timeout = '5min'; ANALYZE matches, match_players; SELECT refresh_window_stats(14);` |
| 정리 | 백엔드 (`npm run collect -- purge --yes`) | 수동, 사용자 확인 뒤 | `purge_old_games(21)`: 시작 시각이 21일 넘은 게임 삭제 |

- **14일 창:** 집계 시각 기준 `[지금 − 14일, 지금)`에 시작한 완료 게임(10줄)만 센다.
- **21일 보관:** 원본은 창 14일 + 여유 7일만 둔다. 집계 전에 지우지 않는다 (집계 → 정리 순서).
- 지금 21일 넘은 게임은 0개다. 가장 오래된 게임(2026-09-30)이 2026-10-21에 21일을 넘는다.
- 수집이 끝나도 바로 집계하지 않는다. 다음 05:00에 반영된다. 바로 보려면 백엔드 `npm run collect -- aggregate`(같은 순서)를 쓴다.
- 집계가 실패하면(창 안 게임 0개, 시간 초과) 전체가 롤백되어 **이전 집계가 그대로 남는다.**

## 4. 함수와 뷰

요약: 집계 함수 2개, 보조 함수 2개, 티어 계산 뷰 1개다. 모두 DB 주인 계정(백엔드)만 쓸 수 있다.

| 이름 | 하는 일 | 부르는 법 |
|------|---------|-----------|
| `refresh_window_stats(p_days int = 14, p_until timestamptz = now())` | 창 안 완료 게임으로 집계 7개를 지우고 다시 센다. 결과 요약 jsonb 반환. 게임 0개면 오류 P0002 (기존 집계 유지). 동시 호출은 advisory lock으로 차례로 | `ANALYZE matches, match_players;` 뒤에 `SELECT refresh_window_stats(14);` (`p_until`은 테스트용) |
| `purge_old_games(p_keep_days int = 21)` | `game_start_at < now() − p_keep_days일`인 게임 삭제 (`match_players` 함께). 지운 게임 수 반환. 14 미만이거나 현재 창보다 짧으면 오류 | `SELECT purge_old_games(21);` |
| `patch_sort_key(text)` | `'16.9'` → `{16,9}`. 패치를 숫자 순으로 정렬 | `ORDER BY patch_sort_key(patch) DESC` |
| `tier_from_score(numeric)` | 티어 점수 → 1~5티어 | 뷰 안에서 사용 |
| `champion_tier_view` | `champion` + `stats_window`로 승률·픽률·밴률·보정 승률·티어 점수·티어 계산. 50판 미만은 티어 NULL | `SELECT * FROM champion_tier_view WHERE position = $1 ORDER BY tier NULLS LAST, tier_score DESC` |

- 공식과 기준값: 계약 9-2, 9-3. 기준값을 바꿀 때는 `!db`가 새 마이그레이션으로 바꾼다.
- 집계는 개수만 저장한다. 비율과 티어는 조회할 때 계산하므로 공식을 바꿔도 다시 집계할 필요가 없다.

## 5. 보안

요약: 브라우저용 키로는 아무것도 읽거나 부를 수 없다. 백엔드만 서버용 접속 정보로 쓴다.

| 항목 | 현재 상태 |
|------|-----------|
| RLS | public 테이블 12개(`schema_migrations` 포함) 모두 켜짐, 정책 0개 |
| 테이블·뷰 권한 | `anon`·`authenticated` 권한 회수 (`REVOKE ALL`). 지금 SELECT 가능한 객체 0개 |
| 함수 권한 | 4개 모두 `postgres`, `service_role`만 실행. `PUBLIC`·`anon`·`authenticated` 회수 |
| 뷰 | `security_invoker = true` (RLS를 우회하지 않음) |
| Supabase 기본 권한 | `pg_default_acl`이 새 객체에 `anon`·`authenticated` 권한을 준다. 그래서 새 객체는 만들 때마다 `REVOKE`하고, 테스트 `006`이 스키마 전체를 자동 검사한다 |
| pg_cron 권한 | `cron.schedule` 등에 확장 기본값 `PUBLIC` EXECUTE가 있다. 하지만 `anon`·`authenticated`는 `cron` 스키마 USAGE가 없어 실제로 부를 수 없다 (42501 확인). **기본값 유지**로 결정 (확장 주인 권한이라 회수도 안 될 가능성이 큼). 테스트 `011`이 USAGE가 생기면 실패한다 |
| 비밀값 | `DATABASE_URL`은 루트 `.env`에만. 문서·로그·커밋에 출력하지 않는다 |

## 6. 운영 방법

요약: 마이그레이션과 검증은 `db/`에서 npm 명령으로 한다. 적용된 SQL 파일은 절대 고치지 않는다.

`db/` 폴더에서 실행 (`.env`는 저장소 루트):

| 명령 | 하는 일 |
|------|---------|
| `npm run migrate` | 아직 적용하지 않은 파일만 순서대로 적용 (파일 1개 = 트랜잭션 1개, 실패하면 멈춤) |
| `npm run migrate:status` | 파일별 적용 여부, 체크섬 불일치 표시 |
| `npm run migrate:fresh-check` | 임시 스키마에 001부터 전부 적용해 보고 항상 ROLLBACK |
| `npm run verify` | 실제 스키마에서 `db/tests/*.sql` 실행 (항상 ROLLBACK, 전후 줄 수 비교) |
| `npm run verify:fresh` | 임시 스키마에 마이그레이션을 적용한 뒤 테스트 실행 |

예약 작업 결과 확인:

```sql
SELECT status, return_message, start_time, end_time
FROM cron.job_run_details
WHERE jobid = (SELECT jobid FROM cron.job WHERE jobname = 'tiergg_daily_refresh')
ORDER BY start_time DESC LIMIT 7;

SELECT aggregated_at, games FROM stats_window;  -- 하루를 크게 넘었으면 집계가 멈춘 것
```

- Supabase 대시보드 Integrations → Cron에서도 같은 기록을 볼 수 있다.
- 작업 멈추기: `SELECT cron.unschedule('tiergg_daily_refresh');` (시각·명령 변경은 새 마이그레이션으로)

새 마이그레이션 추가:

1. `db/migrations/`에 마지막 번호보다 큰 번호로 새 파일을 만든다 (다음은 `016_….sql`).
2. 적용된 파일(001~015)은 고치지 않는다. 고치면 체크섬 불일치로 실행기가 멈춘다.
3. 새 테이블·뷰·함수·시퀀스는 RLS를 켜고 `anon`·`authenticated`에서 `REVOKE`한다.
4. 삭제처럼 되돌릴 수 없는 SQL은 실행 전에 사용자 승인을 받는다.
5. `migrate:fresh-check` → `verify:fresh` → `migrate` → `verify` 순서로 확인한다.

## 7. 용량과 성능

요약: 지금 90MB이고, 본 수집 규모에서도 약 180MB 안으로 예상한다. 실제 집계는 3~4초다.

| 항목 | 값 |
|------|----|
| 지금 DB 크기 | 90MB / 500MB |
| 가장 큰 테이블 | `match_players` 60MB (본문 9MB + 인덱스 51MB) |
| 집계 테이블 7개 합계 | 약 10MB (`champion_item` 7.5MB가 대부분) |
| 본 수집 예상 | 14일 창 최대 25,000게임, 원본 21일 약 37,500게임 → 합계 약 165~180MB (계약 1-2) |
| 실제 예약 작업 시간 | 2026-10-14 3.3초, 2026-10-15 3.6초 (약 3,800~3,950게임, `ANALYZE` 포함) |
| 시험 측정 (롤백) | 5,000게임 약 1.1초, 25,000게임 약 5~7초. 5분 제한까지 여유가 크다 |

- `match_players` 인덱스(51MB)는 39,750줄치고 크다. 지난 검토의 대량 롤백 시험이 남긴 빈 공간으로 보인다. 본문 1줄은 약 235B라 계약의 1줄 400B(인덱스 포함) 추정과 맞는다.
- 집계 직전 `ANALYZE`는 꼭 필요하다. 원본 통계가 틀리면 5,000게임도 2분을 넘긴다.
- 집계 시간은 `champion_item` 줄 수에 가장 크게 좌우된다.

## 10. 해결되지 않은 점

요약: 동작을 막는 문제는 없다. 다음 `!db` 변경과 운영에서 챙길 것들이다.

1. **룬 1순위와 2순위가 사실상 같다.** 보조 룬 2개의 순서만 다른 페이지를 다른 조합으로 센다 (프론트 검토 기준 챔피언 71/173명, 지금 스냅숏은 챔피언 × 포지션 104개). `!db` 변경 04에서 집계 때 보조 룬을 정렬해 하나로 묶을 예정이다.
2. **계약 문구가 실제 수집과 다르다.** 계약 1-3·10장은 "티어당 100명"인데, 테스트 수집은 사용자 결정으로 티어당 250명(765명)으로 했다. 다음 `!db` 변경 때 문구를 고친다.
3. **`ranked_players` 테이블 주석이 아직 "각 50명"이다.** 동작 영향은 없다. 다음 마이그레이션(016~)에서 주석만 바꾼다.
4. **예약 작업이 실패해도 알림이 없다.** `cron.job_run_details`나 `stats_window.aggregated_at`을 누가 봐야 안다. 백엔드 API의 `aggregatedAt`·`isStale`로 확인하고, 알림은 아직 계획이 없다.
5. **무료 플랜은 7일 동안 쓰지 않으면 일시정지된다.** 일시정지 중에는 예약 작업도 돌지 않는다. 대시보드에서 다시 켜야 하며, 예약 작업이 일시정지를 막는다고 가정하지 않는다.
6. **새 수집이 없으면 집계 창이 비어 간다.** 마지막 게임이 2026-10-14 15:40 UTC라, 수집 없이 2026-10-28 20:00 UTC(10-29 05:00 KST) 집계부터는 0게임(P0002) 실패가 나고 이전 집계가 계속 보인다. 수집은 지금 사람이 직접 돌린다.
7. **오래된 원본 삭제가 수동이다.** 2026-10-21부터 21일 넘은 게임이 생긴다. 백엔드 `purge --yes`를 사용자가 확인하고 실행해야 한다.
8. **안 쓰는 인덱스가 있다.** `match_players (champion_id, team_position)` 인덱스(10MB)는 집계가 쓰지 않는다 (스캔 7회). 본 수집 뒤에도 안 쓰이면 새 마이그레이션으로 삭제를 제안한다.
9. **`match_players` 인덱스에 빈 공간이 많다.** 인덱스 51MB가 본문 9MB보다 훨씬 크다. 지금 용량에는 문제없고, 필요하면 `REINDEX`를 사용자 승인 뒤 검토한다.
10. **계약 보안 장(11장)에 pg_cron 권한 판단이 없다.** "`cron` 스키마 USAGE 없음, `PUBLIC` 기본값 유지"를 다음 계약 수정 때 한 줄 넣는다.
11. **테스트 `011`의 cron 함수 검사가 일부만 본다.** `schedule`·`unschedule` 2개만 직접 부여를 검사한다. 스키마 USAGE 검사가 막고 있어 위험은 없고, 다음 테스트 수정 때 `cron` 함수 전체로 넓힌다.
12. **본 수집(에메랄드 이상 4 : 4 : 2)은 아직 정하지 않았다.** 그때 `PLATINUM`을 허용 값에서 빼려면 `PLATINUM` 표본을 먼저 처리해야 CHECK 변경이 성공한다 (삭제라 승인 필요).
13. **계약 9-4의 `ANALYZE` 이유 칸이 2만 5천 게임 수치만 든다.** 작은 수집에서는 빼도 되는 것처럼 읽힐 수 있다. 5,000게임도 통계가 틀리면 2분을 넘겼다(`ANALYZE` 뒤 1.6초). 다음 계약 수정 때 한 줄 넣는다. 지금은 예약 작업 명령이 항상 `ANALYZE`를 먼저 해서 동작 문제는 없다.
14. **티어 기준값과 스킬 11레벨 제외 비율을 실제 분포로 다시 보지 않았다.** 기준값(50판, 경계 53.0 등)은 샘플로만 정했다. 본 수집 뒤 티어 분포와 포지션별 `length(skill_order) < 11` 비율을 재고, 바꿀 때는 새 마이그레이션으로 한다.

16. **실행기는 마지막보다 작은 번호의 새 파일도 경고 없이 적용한다.** 새 파일 번호는 항상 마지막보다 크게 붙인다 (다음은 016). 필요하면 실행기에 경고를 넣는다 (`db/scripts/` 수정이라 승인 필요).
