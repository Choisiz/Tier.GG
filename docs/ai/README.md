## 1. 무엇을 만드나

전적 검색에서 한 판을 고르면, 그 판을 **라인전 · 교전 · 운영**으로 나눠 좋은 점과 부족한 점, 결정적 장면, 요약을 알려 줍니다.

예시 (세나 서폿, 23분 패배)

> 라인전에서 밀렸고, 오브젝트 싸움과 그 밖의 운영 모두 부족했습니다. 15분 바텀 싸움에서 골드 격차가 3,900 넘게 벌어지며 승부가 기울었습니다.

## 2. 어떻게 동작하나

| 순서 | 담당 | 하는 일 | 비유 |
|------|------|---------|------|
| 1 | 코드 (판정 엔진) | Riot 데이터로 지표를 계산하고 A~E 등급, 총점, 결정적 장면을 정한다 | 채점표 |
| 2 | RAG | 그 판의 상황(유형·과목·등급)에 맞는 해석 문서를 찾아온다 | 해설집 |
| 3 | LLM | 1·2의 결과만 근거로 문장을 쓴다 | 선생님 |
| 4 | 코드 (검증기) | LLM 문장의 숫자·방향이 1과 맞는지 확인한다. 틀리면 1번 다시 쓰게 하고, 그래도 틀리면 기본 문장으로 바꾼다 | 검수 |

- 판단은 코드가 하고 LLM은 설명만 합니다. 그래서 LLM이 숫자를 지어내거나 판정을 바꿀 수 없습니다.
- RAG는 점수를 바꾸지 않습니다. 같은 "시야 E"에 "서폿은 용 1분 전 제어 와드를 먼저 사라" 같은 구체적인 조언을 붙이는 재료입니다.

## 4. 단계별 설명

### 1단계: 판정 엔진 ✅

**만든 것**: 한 판의 match·timeline 데이터를 넣으면 등급·총점·결정적 장면·요약 판정이 JSON으로 나오는 코드 (`backend/src/analysis/`). LLM·RAG·DB를 쓰지 않아 비용이 없습니다.

**확인 방법**: 개발자 컴퓨터에서 명령어로 실행합니다.

```bash
npm run analyze -- --match test/fixtures/KR_8437852704.match.json --timeline test/fixtures/KR_8437852704.timeline.json --participant 5
```

**결과 (세나 판, 엔진 버전 2026-11-02.2)**

| 항목 | 결과 |
|------|------|
| 라인전 | 열세 (골드 3,958:4,661, 레벨 8:8, KDA 1:5) |
| 교전 | 부족, 총점 25 (딜 C · 시야 E · 이득 E · 오브젝트 C) |
| 운영 | 부족, 총점 16.25 (이득 E · 단독 C · 사이드 B · 평소 시야 E) |
| 결정적 장면 | 15.1~15.9분 (+3,895) · 16.7~17.1분 (+3,887) · 22.2~22.9분 (−465) |

검증: 타입 검사·린트 오류 0, 테스트 246개 모두 통과.

**구현 중 정한 것 (2026-11-02)**

| 항목 | 결정 |
|------|------|
| 딜 등급 | 반올림하지 않고 판정 (−2.75%p는 C) |
| 결정적 장면 | 격차 3,000 이상을 격차 순으로 먼저, 남은 자리는 킬 5개 이상을 킬 순으로 |
| 경계값 정정 | 검산 스크립트의 영혼 용 오류를 고쳐 다시 계산. 정글 오브젝트 A 82 이상, 교전 이득 A 78% 이상 |
| 서폿 분류 수정 | 카르마 → 유틸서폿, 모르가나 → 딜서폿, 라칸 → 탱서폿. 세트는 보류 |
| 딜 구간 평균이 등급 사이 정확히 중간일 때 | 높은 등급으로 (예: D + A → B) |

### 2단계: LLM 문장 생성 (RAG 없음)

**만들 것**
- 판정 결과를 Claude에게 보내 문장을 받는 코드
- 숫자 검증기: 문장 속 숫자가 계산값과 같은지, 좋은 점·부족한 점 칸이 판정과 같은지, 등급 글자나 총점이 들어가지 않았는지 검사
- 기본 문장(템플릿): LLM이 실패하면 코드가 "15분 골드가 상대보다 703 적었습니다" 같은 문장을 대신 만듦

**확인 방법**: 개발자 컴퓨터에서 명령어로 실행. 유료 호출이라 **예상 비용을 먼저 보여드리고 승인받은 뒤** 실행합니다.

**왜 RAG 없이 먼저?** 이 결과가 **비교 기준선**입니다. 4단계에서 같은 판으로 RAG를 붙여 다시 만들고, "근거 없는 주장 비율"이 얼마나 줄었는지 숫자로 비교합니다.

**예상 비용**: 판당 Sonnet 약 $0.02, Haiku 약 $0.002 (참고 가격 기준 추정, 2단계에서 실측)

### 3단계: 벡터 DB 준비

**만들 것** (`!db`): Supabase에 벡터 확장(pgvector)을 켜고, 해석 문서 조각을 담을 테이블과 검색 함수를 만듭니다.

- 저장하는 것: 우리가 쓴 해석 문서, 라이엇 공식 챔피언 설명
- 저장하지 않는 것: 플레이어 성적 지표 (기존 결정 유지)
- 용량: 조각 약 1,000개에 약 4MB. 무료 플랜 500MB에 영향 작음

DB 변경이라 항상 전체 Review를 거칩니다.

### 4단계: RAG 붙이기

**만들 것**
1. **해석 문서**: Claude가 설계 문서를 바탕으로 초안을 쓰고, 사용자가 롤 지식으로 고칩니다. 첫 묶음은 50~80조각입니다. 조각 하나는 관점 하나, 2~5문장입니다.

   > 딜서폿의 교전 딜이 낮을 때: 딜서폿은 오브젝트 싸움에서 원딜과 딜을 나눠 맡는 역할이다. 비중이 낮으면 싸움 전에 체력이 깎였거나 사거리 밖에서만 맴돌았을 가능성이 있다.

2. **임베딩·저장**: 조각을 벡터로 바꿔 3단계 테이블에 넣는 명령. 바뀐 조각만 다시 넣습니다.
3. **검색**: 먼저 유형·영역·과목·좋음/부족으로 거르고, 그 안에서 지금 상황에 뜻이 가장 가까운 조각을 고릅니다. 판당 최대 8조각.
4. **보조 자료**: 분석한 챔피언과 상대 라이너의 공식 설명, 우리 DB의 빌드 통계 (판정 없이 참고만)

**확인 방법**: 2단계와 같은 20판으로 다시 만들어 기준선과 비교합니다.

### 5단계: 분석 API

1~4단계 부품을 묶어 사이트가 부를 수 있게 엽니다.

- 사이트에서 "분석"을 누르면 → 서버가 타임라인을 받아 → 엔진 → RAG → LLM → 검증 → 결과 반환
- **캐시**: 같은 판을 다시 누르면 저장된 결과를 줘서 LLM 비용이 다시 들지 않음
- **하루 상한**: LLM 비용이 튀지 않게 하루 분석 횟수 제한
- **오류 처리**: Riot 키 만료는 오류로 알리고, LLM 실패는 기본 문장으로 대신 답함

### 6단계: 피드백 화면

분석 버튼과 결과 화면입니다. 정적 HTML 목업으로 모양을 먼저 승인받고 만듭니다.

### 7단계: 품질 평가와 재조정

| 무엇을 재나 | 목표 (초안) |
|-------------|-------------|
| 최종 응답의 틀린 숫자 | 0개 (검증기가 보장) |
| 근거 없는 주장 비율 | 5% 이하 |
| 검색이 맞는 조각을 가져온 비율 | 상위 4개 안에 80% 이상 |
| RAG 효과 | RAG 켬이 끔보다 같거나 좋음 |
| 응답 시간 | 95%가 20초 안 |

결과를 보고 등급 경계와 총점 경계(70·40)를 다시 맞추고, Sonnet과 Haiku를 비교해 모델을 정합니다.

## 5. 정한 것

| 항목 | 내용 |
|------|------|
| 영역 | 라인전(상대 라이너 대비) · 교전(오브젝트 앞뒤 40초 싸움) · 운영(그 밖) |
| 유형 | 10개: 탱/딜 × 탑·정글·미드, 원딜, 탱/딜/유틸 서폿 |
| 등급 | 과목마다 A~E, 실제 200판 분포로 경계를 정함 |
| 총점 | 반영 비율 × 등급 점수(A 100 · B 75 · C 50 · D 25 · E 0%). 화면에 숫자는 안 보임 |
| 문장 | A·B는 좋은 점, D·E는 부족한 점, C는 말하지 않음 |
| 결정적 장면 | 골드 격차 3,000 이상 변화 또는 킬 5개 이상 싸움, 최대 3개 |
| 요약 | 라인전 우세/비슷/열세 + 교전·운영 잘함/보통/부족 + 결정적 장면 1개 |
| LLM | Claude (Anthropic API) |
| 테스트 데이터 | 실제 판을 닉네임·계정 ID를 가려 저장소에 보관 |
| 비용 규칙 | 유료 API를 부르는 실행은 예상 비용을 먼저 보여 주고 승인받음 |

| 정할 것 | 언제까지 |
|---------|----------|
