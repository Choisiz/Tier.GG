## 1. 무엇을 만드나

- 요약: 전적 검색에서 한 판을 고르면, 그 판을 **라인전 · 교전 · 운영**으로 나눠 좋은 점·부족한 점·결정적 장면·요약을 알려 준다.

| 블록 | 내용 |
|------|------|
| 요약 | 이 판을 한두 문장으로 |
| 라인전 | 상대 라이너보다 골드·레벨·KDA가 높았나 |
| 교전 | 오브젝트(용·바론·전령·유충)를 두고 벌어진 싸움 |
| 운영 | 그 밖의 과정 (싸움 밖 이득, 단독 킬·데스, 사이드, 파밍, 평소 시야) |
| 결정적 장면 | 골드 격차가 크게 바뀌었거나 킬이 많이 난 싸움 최대 3개 |

예시 (세나 서폿, 23분 패배)

> 라인전에서 밀렸고, 오브젝트 싸움과 그 밖의 운영 모두 부족했습니다. 15분 바텀 싸움에서 골드 격차가 3,900 넘게 벌어지며 승부가 기울었습니다.

## 2. 전체 흐름

- 요약: 판단은 코드가, 설명은 LLM이 한다. RAG는 설명의 재료(해설집)다.

```
[Riot match + timeline]
        │
        ▼
① 판정 엔진 (코드)  ──── 등급·총점·말할 순서·결정적 장면·근거 숫자(facts)
        │
        ├──► ② RAG 검색 ──── 이 판 상황에 맞는 해석 문서 조각 몇 개
        │                     (4단계부터)
        ▼
③ LLM (Claude) ──────── 위 두 가지만 보고 문장 작성 (정해진 JSON 형식)
        │
        ▼
④ 검증기 (코드) ──────── 숫자·방향·금지어 검사 → 틀리면 1번 다시 → 그래도 틀리면 기본 문장
        │
        ▼
[피드백 결과]
```

| 순서 | 담당 | 하는 일 | 비유 |
|------|------|---------|------|
| ① | 코드 | 지표 계산, A~E 등급, 총점, 결정적 장면 | 채점표 |
| ② | RAG | 유형·과목·등급에 맞는 해석 문서 검색 | 해설집 |
| ③ | LLM | ①·②만 근거로 문장 작성 | 판결문을 쓰는 서기 |
| ④ | 코드 | LLM 문장이 ①과 맞는지 검사 | 검수 |

- LLM이 하는 일: 사실을 엮어 이야기로 만들기, 무엇부터 말할지 정리, 근거 있는 범위의 조심스러운 해석("~한 것으로 보입니다"), 읽기 좋은 말투.
- LLM이 못 하는 일: 판정 바꾸기, 코드가 주지 않은 숫자 쓰기, 코드가 계산하지 않은 새 평가.
- RAG가 없으면 LLM은 자기가 원래 알던 롤 지식으로 조언을 붙인다. 그 지식은 오래됐거나 일반론이거나 우리 관점과 다를 수 있고, 출처를 확인할 수 없다. RAG는 **검수한 참고서**를 근거로 쓰게 하고, 문장마다 어떤 조각을 썼는지 ID가 남는다.

## 3. 진행 상황

| 단계 | 영역 | 내용 | 상태 |
|------|------|------|------|
| 1 | `!ai` | 판정 엔진 (코드만) | ✅ 완료 (Review 통과, 2026-11-02) |
| 2 | `!ai` | LLM 문장 생성 + 숫자 검증 (RAG 없음 → **비교 기준선**) | ✅ Build 완료, Review 조건부 통과 (사용자 채점 대기) |
| 3 | `!db` | 벡터 DB 준비 (pgvector) | ✅ 완료 (변경 05, v0.5.4) |
| 4 | `!ai` | RAG 붙이기: 해석 문서 작성·저장·검색 | ✅ Build 완료 (2026-11-04), 독립 Review·사용자 채점 대기. Q2 구체적 조언 Build 완료 (2026-11-10, 사용자 채점 대기) |
| 5 | `!백엔드` | 분석 API (사이트가 부를 수 있게 묶기) | ✅ 완료 (2026-11-03, 실제 LLM 확인) |
| 6 | `!프론트` | 피드백 화면 (매치 행 펼침 안 "AI 분석하기") | ✅ 완료 (2026-11-03) |
| 7 | `!ai` | 고정 판 세트로 품질 평가, 기준 재조정, 모델 비교 | 대기 |

- 계약 순서(`!db` → `!백엔드` → `!프론트`)는 3 → 5 → 6단계로 지켜진다.
- 사용자 요청(2026-11-03)으로 5·6단계를 먼저 했다. RAG(3·4단계)는 나중에 붙이며, API·화면 모양은 그대로 둔다.
- 사용하려면 `.env`에 `FEEDBACK_ENABLED=true`, `FEEDBACK_LLM_ENABLED=true`, `FEEDBACK_API_BUDGET_USD`(예: 0.50)를 넣고 백엔드를 다시 켠다. 기본은 꺼짐(실수로 유료 호출이 나가지 않게).
- 2단계 결과와 4단계 결과를 같은 판으로 비교해 "RAG를 붙였더니 근거 없는 주장이 몇 % 줄었다"를 숫자로 확인한다.

## 4. 단계별 설명

### 1단계: 판정 엔진 ✅

- 요약: 한 판의 match·timeline을 넣으면 판정 JSON이 나오는 코드. LLM·RAG·DB·네트워크를 쓰지 않아 비용이 없다.

**위치와 구성** (`backend/src/analysis/`)

| 파일 | 하는 일 |
|------|---------|
| `rules.ts` | 모든 숫자 기준 (반영 비율, 등급 경계, 기대 딜 비중, 점수). **기준을 바꾸려면 이 파일만 고친다** |
| `role.ts` | 유형 10개 판별 (Data Dragon 첫 태그 + 덮어쓰기 목록) |
| `timeline.ts`, `fights.ts` | 타임라인 정리, 싸움 묶기(20초), 오브젝트 창(앞뒤 40초) |
| `laning.ts` | 라인전 (기준 시점, 골드·레벨·KDA 비교) |
| `fight.ts`, `macro.ts` | 교전 4과목, 운영 5과목 등급 |
| `score.ts` | 등급 → 점수, 총점, 말할 순서 |
| `keyMoments.ts`, `summary.ts` | 결정적 장면, 요약 판정 |
| `index.ts`, `types.ts` | 진입 함수와 결과 타입 |

**실행** (개발자 컴퓨터, `backend/` 폴더에서)

```bash
npm run analyze -- --match test/fixtures/KR_8437852704.match.json --timeline test/fixtures/KR_8437852704.timeline.json --participant 5
```

**출력 일부** (교전 시야 과목)

```json
{ "id": "fight.vision", "weight": 30, "grade": "E", "score": 0,
  "facts": { "objectives": 4, "points": 2, "perObjective": 0.5 } }
```

- `facts`는 그 판정의 근거 숫자다. 2단계에서 LLM이 쓸 수 있는 숫자는 이것뿐이고, 검증기가 대조하는 기준도 이것이다.

**결과 (세나 판, 엔진 버전 2026-11-02.2)**

| 항목 | 결과 |
|------|------|
| 라인전 | 열세 (골드 3,958:4,661, 레벨 8:8, (K+A)−D 1:5) |
| 교전 (딜서폿) | 부족, 총점 25 (딜 C · 시야 E · 이득 E · 오브젝트 C) |
| 운영 | 부족, 총점 16.25 (이득 E · 단독 C · 사이드 B · 평소 시야 E) |
| 결정적 장면 | 15.1~15.9분 (+3,895) · 16.7~17.1분 (+3,887) · 22.2~22.9분 (−465) |

**검증**: 타입 검사·린트 오류 0, 테스트 246개 통과(엔진 82개). Review에서 같은 판 정글 2명을 별도 스크립트로 다시 계산해 16개 값이 모두 일치.

**구현 중 정한 것 (2026-11-02)**

| 항목 | 결정 |
|------|------|
| 딜 등급 | 반올림하지 않고 판정 (−2.75%p는 C) |
| 딜 구간 평균이 등급 사이 정확히 중간 | 높은 등급으로 (예: D + A → B) |
| 결정적 장면 | 격차 3,000 이상을 격차 순으로 먼저, 남은 자리는 킬 5개 이상을 킬 순으로 |
| 경계값 정정 | 검산 스크립트의 영혼 용 오류(두 번째 용을 영혼 용으로 셈, 200판 중 185판)를 고쳐 다시 계산. 정글 오브젝트 A 82 이상, 교전 이득 A 78% 이상 |
| 서폿 분류 수정 | 카르마 → 유틸서폿, 모르가나 → 딜서폿, 라칸 → 탱서폿. 세트는 보류 |
| 테스트 데이터 | 세나 판 원본을 닉네임·계정 ID를 가려 `backend/test/fixtures/`에 보관 |

**남은 점**: 다시하기(3~4분) 판도 등급이 나온다 → 5단계에서 "분석할 판 범위"로 해결. 챔피언 분류 데이터가 테스트용 패치(16.21.1) 고정 → 5단계에서 판의 패치에 맞게 공급.

### 2단계: LLM 문장 생성 (RAG 없음) ✅

- 요약: 1단계 판정 결과를 Claude Opus 5.5에 보내 문장을 받고, 코드가 검사한다. RAG 없이 만든 이 결과가 **비교 기준선**이다.

**만든 것** (`backend/src/analysis/llm/`, `analysis/feedback.ts`, `cli/feedback.ts`)

| 부품 | 하는 일 |
|------|---------|
| `facts.ts` | 엔진 결과에서 LLM이 쓸 수 있는 숫자 목록을 만든다 (등급·점수·총점·반영 비율은 뺌) |
| `prompt.ts`, `schema.ts` | 고정 규칙(시스템, 캐시됨) + 이 판의 판정·facts. 답은 정해진 JSON 모양으로만 |
| `client.ts` | Anthropic SDK를 부르는 유일한 파일. 모델 `claude-opus-5-5`, 생각 깊이 `low`, 최대 출력 3,000토큰(재시도 1,500) |
| `verify.ts` | 검증기 (아래) |
| `template.ts` | LLM이 실패할 때 쓰는 기본 문장 26종 + 요약·결정적 장면용 |
| `ledger.ts`, `pricing.ts` | 호출마다 비용을 장부(`backend/test/eval/usage-ledger.jsonl`)에 기록, 예산 상한 검사 |
| `fakeClient.ts` | 테스트용 가짜 응답 (0원) |

**프롬프트 규칙**: 판정 바꾸지 않기, facts 숫자만 그대로 쓰기, 등급 글자·총점 금지, 추정 해석은 "~것으로 보입니다" + 근거, 존댓말·한 문장 약 120자 이내.

**LLM이 채우는 JSON (모양)**

```jsonc
{
  "summary": { "text": "…", "factIds": ["laning.opponent", "keyMoment.0.gapChangeAbs"] },
  "sections": {
    "laning": { "good": [], "bad": [ { "subjectId": "laning.gold", "text": "…", "factIds": ["laning.gold.diffAbs"] } ] },
    "fight": { … }, "macro": { … }
  },
  "keyMoments": [ { "index": 0, "text": "…", "factIds": ["keyMoment.0.gapChangeAbs"] } ]
}
```

**검증기가 보는 것**: 모양 · 방향(좋은 점/부족한 점 칸 안 단어, 요약 판정어, 결정적 장면 벌어짐/좁혀짐/앞선 팀 바뀜) · 숫자(문장 속 숫자가 그 문장의 facts와 같은지, 숫자 뒤 단위어가 그 fact에 맞는지) · 금지어 · 길이 · 챔피언 이름. 틀린 문장만 1번 다시 쓰게 하고, 그래도 틀리면 그 문장만 기본 문장으로 바꾼다.

**실행** (`backend/`에서. 플래그 없이 실행하면 예상 비용만 보여 주고 호출하지 않음)

```bash
npm run feedback -- --set test/eval/set5            # 미리보기 (0원)
npm run feedback -- --set test/eval/set5 --replay   # 저장된 응답으로 재생 (0원)
npm run feedback -- --set test/eval/set5 --yes      # 실제 호출 (유료)
```

**기준선 결과** (평가 세트 5판: 딜서폿·탱탑·딜정글·딜미드·원딜, 2026-11-04 Q1 뒤 다시 만듦)

| 항목 | 결과 |
|------|------|
| 문장 | 54개 |
| 첫 번째에 검증 통과 | 52개 (96.3%) (지난번 51개) |
| 재시도로 고쳐짐 / 기본 문장 | 1개 / 1개 (지난번 3개 / 0개) |
| 최종 틀린 숫자 · 방향 · 금지어 | 0 · 0 · 0 |
| 판당 평균 | $0.079, 약 14초 (2판째부터 캐시로 판당 약 $0.02 절약) |
| 누적 비용 | $0.8409 / 2단계 한도 $1 |

**알게 된 점과 알려진 한계**
- 숫자는 정확하지만 **숫자를 읽어 주는 수준**이고 조언이 없다 → 4단계 RAG로 비교할 부분.
- Review가 찾은 오해 문장 3종(역전 싸움을 "격차 300 벌어짐", 상대 팀 킬을 "5데스", 칸 안 반대 방향 단어 미검사)은 **Q1(2026-11-04)에서 고쳤다**: 역전 장면은 "앞선 팀이 우리 팀 → 상대 팀, 골드 약 4,400 손해"로 쓰고, 검증기가 단위어와 칸 안 방향 단어를 본다. 새 기준선 54문장에서 오해 0.
- 남은 한계: 중후반 파밍 칸에 "15분" 값이 없어 재시도·기본 문장이 생긴다. 방향 검사는 단어 목록이라 주어를 상대로 바꾼 맞는 문장도 막을 수 있다. 단위는 숫자 바로 뒤 단어만 본다.

### 3단계: 벡터 DB 준비

- 요약: Supabase에 pgvector를 켜고, 해석 문서 조각을 담을 테이블과 검색 함수를 만든다 (`!db`, 항상 전체 Review).

| 항목 | 내용 |
|------|------|
| 확장 | `vector` (Supabase 제공) |
| 테이블 `rag_chunk` | 조각 ID, 출처(관점 문서 / 챔피언), 포지션, 유형, 영역, 과목, 좋음/부족, 챔피언 ID, 본문, 본문 해시, 벡터, 임베딩 모델 이름 |
| 검색 함수 | 조건(유형·영역·과목·방향)으로 거른 뒤, 뜻이 가까운 순 상위 N개 |
| 보안 | 기존 테이블과 같이 RLS 켜고 공개 접근 없음 |
| 용량 | 조각 약 1,000개 × 1,024차원 ≈ 4MB. 무료 플랜 500MB에 영향 작음 |

- 저장하는 것: 우리가 쓴 해석 문서, 라이엇 공식 챔피언 설명.
- 저장하지 않는 것: 플레이어 성적 지표 (기존 결정 유지).
- 벡터 크기(차원)는 임베딩 서비스에 따라 정해지므로, 3단계 전에 임베딩 서비스를 골라야 한다.

### 4단계: RAG 붙이기

- 요약: 사용자의 롤 지식을 짧은 관점 조각으로 쓰고, 벡터로 바꿔 저장한 뒤, 판마다 맞는 조각을 찾아 LLM에게 함께 준다.

**① 해석 문서 쓰기** (`docs/ai/knowledge/`, git으로 관리)
- Claude가 설계 문서를 바탕으로 초안 → **사용자가 롤 지식으로 고치고 승인**. 첫 묶음 81조각 (검수 안내·전체 표: `docs/ai/knowledge/README.md`).
- 조각 하나 = 관점 하나, 2~5문장. 숫자 경계값은 쓰지 않는다(숫자의 출처는 `rules.ts` 하나뿐).

```markdown
### fight.damage.SUPPORT_DAMAGE.bad.01 딜서폿의 교전 딜이 낮을 때
- meta: role=SUPPORT_DAMAGE, area=fight, subject=damage, polarity=bad
딜서폿은 오브젝트 싸움에서 원딜과 함께 딜을 나눠 맡는 역할이다. 교전 딜 비중이 낮으면
싸움 전에 체력이 깎였거나 사거리 밖에서만 맴돌았을 가능성이 있다.
```

**② 조각내기·벡터화·저장** (명령 하나)
| 단계 | 방법 |
|------|------|
| 조각내기 | `###` 소제목 단위로 자른다 (관점 하나가 이미 한 조각) |
| 검사 | ID 중복, 메타데이터 누락, 허용되지 않은 값, 너무 긴 조각, 숫자 포함 경고 |
| 벡터화 | 본문이 바뀐 조각만 임베딩 서비스로 보낸다 (비용 절약) |
| 저장 | 3단계 테이블에 덮어쓰기. 지울 때는 미리보기 후 확인 |

**③ 검색** (판마다)
1. 엔진이 고른 "말할 과목"마다 조건으로 거른다: 이 유형(또는 공통) + 이 영역 + 이 과목 + 이 방향(좋음/부족).
2. 그 안에서 "딜서폿 교전 딜 부족, 데스 먼저, 패배" 같은 짧은 질의 문장과 뜻이 가까운 순으로 2개.
3. 전체 최대 8조각 (토큰 비용 상한).
4. 맞는 조각이 없으면 공통 조각으로 넓히고, 그래도 없으면 RAG 없이 쓴다.

- 조건 거르기가 "포지션이 다른 조각이 섞이는 문제"를 막고, 벡터는 **같은 과목 안에서 지금 상황에 더 맞는 조각**을 고른다. 이렇게 조건과 벡터를 섞는 것을 하이브리드 검색이라고 한다.

**④ 보조 자료**: 분석한 챔피언과 상대 라이너의 공식 설명(Data Dragon), 우리 DB의 빌드 통계(판정 없이 참고만, 임베딩하지 않고 그때그때 조회).

**확인 방법**: 2단계와 같은 판 세트로 다시 만들어 기준선과 비교. 검색 평가 질의 20개로 "맞는 조각이 상위에 나왔나"도 잰다.

**결과 (2026-11-04)**
- 조각 81개(유형 파일 57 + 공통 24) 적재. 임베딩은 Voyage `voyage-4`, 실제 9,926토큰(무료 범위).
- 검색 평가: 상위 2개 적중 21/21(100%). 단, 조건 거르기 뒤 후보가 대부분 1~2개라 벡터 순위의 효과는 거의 재지 못한다(갈린 곳은 원딜 두 조각뿐, 맞게 고름).
- 같은 5판: 1차 통과 52/54 → 51/54, 최종 오류 0 → 0, 비용 $0.3948 → $0.5020(입력 약 21% 늘어남). 54칸 중 28칸이 조각을 반영해 "다음 판에는 ~해 볼 수 있습니다" 조언이 붙었다.
- 근거 없는 주장·조언 구체성은 나란히 놓은 채점표(`backend/test/eval/results/*q1-vs-rag.grading.md`)로 사용자가 채점한다.
- 사이트에서 쓰려면 `.env`에 `VOYAGE_API_KEY`와 `FEEDBACK_RAG_ENABLED=true`. 기본은 꺼짐(이전과 같은 문장).
- 계획과 달리 챔피언 설명·빌드 통계는 1차에서 뺐다(RAG 효과만 따로 재려고).

**Q2 보완 (2026-11-10): 구체적인 조언**
- 채점에서 나온 지적("낀"이 무슨 뜻인지 모름, 기준 시간이 없음, "아군 포탑 쪽에 서 볼 수 있습니다" 같은 막연한 조언)을 고쳤다. 원인은 엔진이 합계만 넘겨 **짚을 장면이 없던 것**.
- 엔진이 이제 장면도 넘긴다(점수·등급은 그대로, 50명으로 확인): 오브젝트마다 몇 분·무엇·누가 잡았나·그 전 60초 동안 내 와드 수, 내가 참여한 싸움마다 몇 분·킬 수·누가 먼저 죽었나·어디서(예: "아래쪽 강", "우리 정글 위쪽", "바텀 라인 상대 포탑 쪽"), 단독 킬·데스와 라인전 데스의 시각·지역.
- 문장 규칙: "낀" 대신 "내가 참여한", 교전 문장에 기준 시간("오브젝트를 잡은 시각 앞뒤 40초", "잡기 전 60초"), 조언은 이 판의 장면 하나를 짚고 언제·어디서·무엇을 하라고("다음 판에는 용을 잡기 전 60초 안에 아래쪽 강 입구에 제어 와드를 먼저 두세요"). "~해 볼 수 있습니다"·"이어 가"·장면 없는 조언은 검사기가 막는다. 지식 조각 81개도 "조건 + 구체 행동"으로 다시 썼다.
- 결과(같은 5판, 사용자 승인 뒤 1회): 조언 19문장 **모두 장면을 짚음**, "낀"·막연한 조언 0, 최종 오류 0. 대신 비용 $0.5020 → **$0.8744**, 1차 통과 51 → 46/54. 옛 RAG 조언 21개는 새 검사기에서 모두 실패로 잡힌다. 화면 모양 채점표(사용자 채점 대기): `backend/test/eval/results/2026-11-10T14-29-19-893Z.compare.set5.q1-rag-q2.ui.grading.md`.

### 5단계: 분석 API

- 요약: 1~4단계 부품을 묶어 사이트가 부를 수 있는 API로 연다 (`!백엔드`, 계약 변경이라 전체 Review).

**요청과 응답 (초안)**

```http
POST /api/v1/matches/KR_8437852704/feedback
{ "puuid": "…" }
```

```jsonc
{ "matchId": "KR_8437852704", "role": "SUPPORT_DAMAGE", "mode": "llm",
  "summary": "라인전에서 밀렸고 …",
  "sections": { "laning": { "good": [], "bad": [ … ] }, "fight": { … }, "macro": { … } },
  "keyMoments": [ … ] }
```

- POST인 이유: LLM 비용이 드는 요청이라, 링크 미리보기나 크롤러가 실수로 부르지 않게.
- 응답에 등급·총점 숫자는 넣지 않는다.

**함께 처리하는 것**

| 항목 | 내용 |
|------|------|
| 캐시 | 같은 판·같은 플레이어·같은 규칙 버전이면 저장된 결과를 줌 (LLM 비용 0) |
| 동시 요청 | 같은 판을 동시에 눌러도 LLM은 1번만 |
| 하루 상한 | 하루 분석 횟수 제한 (캐시 적중은 세지 않음) |
| 끄는 스위치 | 환경 변수로 LLM을 끄고 템플릿만 쓰게 |
| Riot 호출 | 판당 2회(match + timeline), 기존 호출 한도 공유 |

**오류 처리**

| 상황 | 응답 |
|------|------|
| Riot 키 만료 | 503 오류 |
| Riot 재시도 소진 | 502 오류 |
| 판이 없음 / 참가자가 아님 | 404 오류 |
| 분석하지 않는 판 (다시하기 등) | 422 오류 |
| LLM 키 문제·한도·시간 초과·거절 | 200 + 템플릿 문장 (사용자는 항상 결과를 받음) |
| RAG 검색 실패 | 200 + RAG 없이 쓴 문장 |

### 6단계: 피드백 화면

- 요약: 분석 버튼과 결과 화면. 정적 HTML 목업으로 모양을 먼저 승인받고 만든다 (CLAUDE.md 10장).
- 정할 것: 화면 위치(매치 행 펼침 / 별도 페이지 / 모달), 기다리는 동안의 표시(최대 수십 초), 템플릿 문장일 때 표시 여부.

### 7단계: 품질 평가와 재조정

- 요약: 고정 판 세트로 같은 지표를 재고, 기준과 모델을 정한다.

| # | 지표 | 목표 (초안) |
|---|------|-------------|
| 1 | 엔진 일치율 (손계산과 비교) | 100% |
| 2 | 숫자 1차 통과율 (LLM 첫 답이 검사 통과) | 90% 이상 |
| 3 | 최종 응답의 틀린 숫자 | 0개 (검증기가 보장) |
| 4 | 방향 불일치 | 0개 |
| 5 | 근거 없는 주장 비율 (사람 채점 → LLM 채점기 보정) | 5% 이하 |
| 6 | 추정 해석 표기("~것으로 보입니다") 준수 | 100% |
| 7 | 검색이 맞는 조각을 상위 4개 안에 가져온 비율 | 80% 이상 |
| 8 | RAG 효과 (같은 판, RAG 끔 vs 켬) | 켬이 같거나 좋음 |
| 9 | 응답 시간 | 95%가 20초 안 |
| 10 | 템플릿으로 바뀐 비율 | 5% 이하 |

- 결과를 보고 등급 경계와 요약 총점 경계(70·40)를 다시 맞추고, Opus·Sonnet·Haiku를 같은 판으로 비교해 서비스 모델을 정한다.

## 8. 용어

| 용어 | 뜻 |
|------|-----|
| LLM | 글을 이해하고 쓰는 AI 모델. 여기서는 Claude |
| RAG | 미리 쌓아 둔 자료에서 관련된 것만 찾아 LLM에게 함께 주는 방식 |

| 기준선 | 비교의 출발점. 여기서는 RAG 없이 만든 2단계 결과 |

| 템플릿 문장 | LLM이 실패할 때 코드가 정해진 틀로 만드는 기본 문장 |
| 구조화 출력 | LLM이 정해진 JSON 모양으로만 답하게 강제하는 기능 |
